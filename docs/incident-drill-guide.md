# インシデント対応 ロープレ（ドリル）手順書

> チームでインシデント対応を練習（ロールプレイ）するための進行手順書。
> 本アプリ（Slack `/incident` + Web ポストモーテム/ランブック）を実際に動かしながら、
> 障害時運用ルール（営業へ一次連絡 → 上長報告 → 役割分担）を体で覚えることを目的とする。
> 関連: [ops-alignment-improvement-plan.md](./ops-alignment-improvement-plan.md) / [MANUAL.md](./MANUAL.md)

---

## 1. 目的とゴール

- 起票（`/incident` または 🆘リアクション）→ 記録 → `/incident end` → ポストモーテム → ランブック の一連を**全員が迷わず**回せるようにする。
- 役割分担（調査役 / 営業連絡役の2役を立ち上げる）を実地で確認する。
- 初動チェックリストの順序（営業連絡 → 上長報告 → 役割分担 → 影響特定）を習慣化する。

**所要時間の目安**: 1シナリオ 15〜25分（対応10〜15分 + 振り返り5〜10分）。

---

## 2. 事前セットアップ（⚠️ 本番に影響させないための安全設定）

ドリルは本番と同じシステムを使うため、**始める前に必ず**以下を設定する。

### 2.1 Backlog 起票を止める / テスト先に向ける（最重要）
ドリルで本物の `Trouble_Report(TR)` に課題を量産しないよう、起票を OFF にする。
```
# ドリル前: Backlog 起票を OFF
AWS_PROFILE=incident-prod node backend/scripts/set-backlog-mode.mjs off
# （もし起票も練習したいなら、TR ではなくテスト用プロジェクトへ）
# AWS_PROFILE=incident-prod node backend/scripts/set-backlog-mode.mjs on WEBG_OTHERS
# 現在値の確認
AWS_PROFILE=incident-prod node backend/scripts/set-backlog-mode.mjs status
```

### 2.2 周知通知（上長・営業へのメンション）を確認
重大度別の周知/エスカレーションは `IncidentNotifyConfig` に従う。
- **未設定（既定）なら通知は飛ばない**ので、そのままならドリルで上長・営業を煩わせない。
- もし本番用に設定済みなら、ドリル中は一時的に空 `{}` にするか、ドリル専用チャンネルだけを宛先にする。
```
# 確認（設定が入っているか）: 値は出さず存在だけ確認したい場合は SST コンソール等で
# ドリル中だけ通知を止める例
AWS_PROFILE=incident-prod npx sst secret set IncidentNotifyConfig '{}' --stage production && AWS_PROFILE=incident-prod npm run deploy:prod
```

### 2.3 リーダー自動招待を止める（テスト時）
本番では起票時に開発リーダー陣が専用chへ自動招集されるが、ドリルでは実際のリーダーを巻き込まないよう **OFF** にする（OFF時は起票者のみ招待）。
```
# ドリル前: リーダー自動招待を OFF
AWS_PROFILE=incident-prod node backend/scripts/set-invite-mode.mjs off
# 現在値の確認
AWS_PROFILE=incident-prod node backend/scripts/set-invite-mode.mjs status
```
> 本番運用に戻すときは `... set-invite-mode.mjs on`（既定メンバーは Kouta Kawaguchi を除く開発リーダー5名）。

### 2.4 ドリル用の「起票元チャンネル」を用意
- 練習は本番運用チャンネル（#ops 等）ではなく、**ドリル用チャンネル**（例: `#incident-drill`）から起票する。起票方法は2通り: **`/incident`** コマンド（モーダルは**タイトルのみ**）、または事象の発言に **🆘（`:sos:`）** を付ける（その発言を種に起票）。
- Bot（`@generosity_incident_management`）をそのチャンネルに `/invite` しておく（起票元への開始通知が届くように）。
- **同じ起票元チャンネルには同時に1件しかアクティブにできない**（重複起票ガード）。複数シナリオを同時にやるなら起票元チャンネルを分ける。基本は**1本ずつ順番に**実施する。

### 2.5 参加者と役割を決める
対応で立ち上げる役割は **「調査役」と「営業連絡役」の2つだけ**（障害時運用ルール）。専用チャンネルの**役割ボタン**で立候補する。**1人が両方を兼ねるのは非推奨**（役割ボタンでも警告される）。

| 役割 | 人数 | やること |
|---|---|---|
| 調査役 | 1〜2 | 専用チャンネルで原因調査・復旧を行う。 |
| 営業連絡役 | 1 | 営業への一次連絡・上長報告など対外コミュニケーションを行う。 |

> ドリル運営上は別途、進行役（インジェクトを出す人）と `/incident` を実行する起票者、Webで振り返りをするレビュー役も必要になるが、これらは**対応の役割ではない**ので、参加者の誰かが兼ねてよい。

## 3. 当日の基本フロー

1. ファシリテーターが「これから SEVx のドリルを始めます」と宣言。
2. 起票・進行担当がドリル用チャンネルで起票 → 専用チャンネル（`inc-...`）が自動生成。起票は次のどちらか:
   - **`/incident`**（引数なしでOK。モーダルは**タイトルのみ**、重要度は既定 SEV2）
   - 事象の発言に **🆘（`:sos:`）** を付ける（その発言を種に起票。Backlog起票ONなら課題もその発言内容で初期起票される）
   - ドリルではリーダー招待OFF（2.3）なので、専用chに入るのは**起票者のみ**。
   - ※ 🆘・:memo: を使うには Slackアプリの再インストール（`reactions:read`＋`reaction_added`）が前提。
3. 全員 専用チャンネルへ移動。ピン留めされた**ボタン式 初動チェックリスト**に沿って進める。
   - 各ステップは完了したら **「完了にする」ボタン**を押す（✅＋誰が/いつ が記録される）。
   - **役割ボタン**で「調査役」「営業連絡役」に立候補（同じ人が両方取ると⚠️警告）。
   - ※ 起票から10分経っても未完了があると、Botが**自動でナッジ**（催促）を投稿する。
4. ファシリテーターが専用チャンネルに**インジェクト**（下記シナリオ）を時間差で投下。
5. 参加者は調査状況を**発言で共有**して応答（＝チャンネルの発言はすべて記録される。状態遷移「調査中→原因特定→対応中→復旧確認中」も発言で表現する）。
   - 本番では、残したい発言に **:memo:** を付けると Backlog 課題へ追記されるが、**ドリル中は Backlog OFF（2.1）なので追記されない**（練習では気にしなくてよい）。
6. 復旧できたら `/incident end` で解決方法を入力してクローズ。
   - クローズ後、**定型フォーマットのトラブル報告**（＜発生日時＞＜時系列＞＜発生事象＞＜原因＞＜影響＞＜対応＞＜今後の対策＞）が専用chに自動投稿される（AI生成のため数十秒かかる）。
7. レビュアーが Web でポストモーテム生成 →（必要なら）ランブック生成。
8. 5〜10分で振り返り（後述）。

## 4. ユースケース例（ドリルシナリオ）

各シナリオは「概要 / インジェクト（ファシリテーター）/ 期待アクション（参加者）/ 打つコマンド・記録例」で構成。**専用チャンネルに投稿した発言がタイムラインに記録され、ポストモーテムの材料になる**ので、発言は具体的に。

### シナリオA｜SEV1 決済APIタイムアウト多発（王道）
**start モーダル**: タイトル `決済APIのタイムアウト多発` / 重要度 `SEV1` / 影響範囲 `本番・全ユーザー、決済が断続的に失敗` / 案件・顧客 `（任意）` / 対外影響 `あり`

**インジェクト（ファシリテーターが時間差で投下）**
1. 「決済APIで5xxが急増。エラー率30%」
2.（3分後）「外形監視で checkout の p99 が 0.8s→8s に悪化」
3.（原因調査が進まなければ）「決済プロバイダのステータスページは正常」

**期待アクション / 記録例（専用チャンネルに投稿）**
```
（起票者）まず営業へ「事象確認・調査中」を一次連絡します ← 初動チェック1
（営業連絡）営業と上長へ第一報入れました ← 初動チェック2
（起票者）調査は@Aさん、営業連絡は@Bさんで ← 初動チェック3（役割分担）
（調査）APIサーバーのDB接続が max=20 に張り付き。プール枯渇
（調査）リトライ経路でコネクションcloseし忘れが原因
```
対応の進み（発言で共有）: `調査中` → `原因特定` → `対応中` → `復旧確認中`
**end 解決方法**: `DB接続リークでプール枯渇。暫定でプール上限20→50に拡張し再起動、エラー率0%に回復。恒久対応はリトライのclose漏れ修正をデプロイ予定。`

---

### シナリオB｜SEV2 画像生成ジョブがキューに滞留
**start モーダル**: タイトル `画像生成ジョブがキューに滞留し完了しない` / `SEV2` / 影響 `画像生成機能、結果が返らない` / 対外影響 `あり`

**インジェクト**
1. 「"生成中のまま返らない" の報告が複数」
2.（2分後）「SQSの滞留メッセージが3,000件超」
3. 「ワーカーが再試行ループしている」

**期待アクション / 記録例**
```
（営業連絡）ユーザー影響あり。CSへ状況共有しました
（調査）壊れた入力画像でワーカーが例外→DLQ未設定で無限再配信
（調査）暫定: 該当メッセージをDLQ退避、ワーカーの例外を握りつぶすよう修正
```
対応の進み（発言で共有）: `調査中`→`原因特定`→`対応中`→`復旧確認中`
**end 解決方法**: `不正入力でワーカーが例外を投げDLQ未設定のため滞留。暫定で問題メッセージをDLQ退避＋例外時も正常終了に修正。恒久対応でDLQ設定と入力バリデーション追加。`

> このシナリオは実際に社内で起きた事象がベース。**「気づくのが遅い」への初動練習**として有効。

---

### シナリオC｜SEV1 デプロイ直後にアプリ起動失敗 → ロールバック
**start モーダル**: タイトル `デプロイ後に本番アプリが起動失敗` / `SEV1` / 影響 `本番サイト全体が5xxでダウン` / 対外影響 `あり`

**インジェクト**
1. 「14:32のデプロイ直後から本番が全ページ500」
2.（1分後）「起動時に環境変数未設定でクラッシュのログ」

**期待アクション / 記録例**
```
（起票者）全断のためまず直前バージョンにロールバックします（復旧優先）
（調査）今回のPRで参照する環境変数名を変えたがSecret未登録だった
（起票者）ロールバック完了、サイト復旧を確認
```
対応の進み（発言で共有）: `調査中`→`原因特定`→`対応中`→`復旧確認中`
**end 解決方法**: `環境変数名変更に対しSecret未登録でLambda起動失敗し全断。直前バージョンへロールバックで復旧（ダウン約9分）。恒久対応はSecret登録後に再デプロイ＋デプロイ前チェックに必須Secret存在確認を追加。`

## 5. 振り返り（ポストモーテム → ランブック）

1. Web アプリ → ヘッダー **Incidents** → 対象インシデント（closed）を開く。
2. **「ポストモーテムを生成」** を押す（closed かつメッセージ1件以上が条件、数十秒）。
3. 生成された「概要 / タイムライン（時刻・担当者入り）/ 根本原因 / 対応内容 / 改善アクション」を全員で確認。
   - 「タイムラインに時刻・担当が正しく出ているか」「解決方法は具体的か」を講評ポイントに。
4. 必要なら **「Runbookを生成」** → 内容を確認して保存（＝再発防止ナレッジ化の練習）。

**講評の観点**
- 初動チェックリストの各ボタンを順に押して進められたか（営業連絡→上長報告→役割分担→影響特定）。
- 役割ボタンで「調査役／営業連絡役」を**分担**できたか（1人2役になっていないか）。
- 会話を専用チャンネルに集約できたか（起票元での対応議論は記録されない）。
- 状況を発言でこまめに共有したか（残したい要点は :memo: で Backlog へ）。
- `/incident end` の解決方法が具体的だったか（PMの質に直結）。

## 6. 後片付け（ドリルデータの掃除）

ドリルで作られたインシデント/チャンネルを片付ける。

- **専用チャンネル**（`inc-...`）: 参加者が各チャンネルで「アーカイブする」を実行（Slack UI）。数が多ければ管理者に依頼。
- **インシデントレコード**: ドリル以外のアクティブ/クローズ済みインシデントが**存在しない**ことを確認のうえ、一括削除スクリプトを使う。
```
# ⚠️ これは全インシデントレコードを削除する。実インシデントがある時期は使わないこと
AWS_PROFILE=incident-prod DRY_RUN=1 node backend/scripts/delete-all-incidents.mjs   # まず件数確認
AWS_PROFILE=incident-prod node backend/scripts/delete-all-incidents.mjs             # 実削除
```
- **設定を元に戻す**:
```
# Backlog を本番運用に戻す（使う場合）
AWS_PROFILE=incident-prod node backend/scripts/set-backlog-mode.mjs on
# リーダー自動招待を本番運用に戻す（使う場合）
AWS_PROFILE=incident-prod node backend/scripts/set-invite-mode.mjs on
# 通知設定をドリル用に空にしていたら本番用へ戻す（該当時のみ）
```

## 7. 進行チェックリスト（コピーして使う）

事前:
- ☐ Backlog を off（or テストプロジェクト）に設定した
- ☐ **リーダー自動招待を off** にした（テスト時は起票者のみ招待）
- ☐ 周知通知（IncidentNotifyConfig）がドリル中に本番宛先へ飛ばない状態を確認した
- ☐ ドリル用チャンネルを用意し Bot を招待した
- ☐ 対応役割（調査役／営業連絡役）を立ち上げる想定を共有した（進行・起票・レビューは参加者が兼任可）

各シナリオ:
- ☐ `/incident`（引数なし）で起票、専用チャンネル生成を確認
- ☐ 初動チェックリストの**ボタンを順に押して**対応（役割ボタンで調査役/営業連絡役を分担）
- ☐ 状況を発言で共有（残したい要点は :memo:）
- ☐ `/incident end` に具体的な解決方法を記入
- ☐ ポストモーテム生成・講評（必要ならランブック生成）

事後:
- ☐ 専用チャンネルをアーカイブ
- ☐ インシデントレコードを掃除（他に実データが無いことを確認）
- ☐ Backlog / リーダー招待 / 通知設定を本番運用に戻した
